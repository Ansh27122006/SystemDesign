SYSTEM DESIGN LAB · MODULE 01

Performance vs Scalability

Two questions that sound similar but demand completely different answers: "is it fast?" and "does it stay fast as more people show up?" This module walks through both with live simulations, real production examples, and a graded activity.

Opening analogy — the restaurant kitchen

One slow chef: a single chef, poorly organized, takes 6 minutes per dish. This is a performance problem — slow at any order volume, even one table.

01 · CORE DEFINITIONS
What each term actually measures

These aren't synonyms. Performance is about one unit of work, right now. Scalability is about the system's behavior as demand grows. A system can be fast and unscalable, or slow and perfectly scalable.

Performance

How quickly a system completes a unit of work under a given, fixed load. It's a snapshot measurement — response time, throughput at a point in time, CPU/memory efficiency.

🍽️ Analogy: how fast one chef plates one dish, with the kitchen at normal capacity.

Scalability

The system's capacity to maintain acceptable performance as load grows, typically by adding resources — more servers, more chefs, more database shards.

05 · REAL-WORLD EXAMPLES
Where teams actually hit these problems
🎬

Netflix — horizontal scaling for traffic spikes

Netflix runs thousands of microservice instances behind load balancers on AWS. During peak evening hours or a big release, it automatically spins up more instances rather than making any single server bigger — pure horizontal scalability.

SCALABILITY WIN
🐌

The classic "N+1 query" bug

A page that loops through 50 items and fires a separate database query for each one will be slow even for a single visitor with a warm cache. Adding more servers doesn't help — every server independently runs the same 50 slow queries. Pure performance bug.

PERFORMANCE BUG
🏦

Legacy banking mainframes

Many core banking systems are extremely fast per-transaction (finely tuned COBOL running on dedicated hardware) but were never designed to scale horizontally, so banks scale them vertically — buying the largest mainframe available, which gets very expensive very fast.

FAST, HARD TO SCALE
🛒

E-commerce during flash sales

A store's checkout might be plenty fast on a normal day, but during a flash sale, traffic jumps 50x in minutes. Teams pre-scale (add servers ahead of time), add caching, and queue-based order processing so the system stays responsive under the spike.

SCALABILITY PLANNING
06 · COMMON CONFUSIONS
What students usually get wrong
✕
"If it's fast, it's scalable."

False. A system can be blazing fast for one user and fall over completely at 1,000 concurrent users if it wasn't designed to distribute load — e.g. it holds everything in memory on one machine.

✕
"Scaling out always fixes slowness."

False. If the root cause is an inefficient algorithm or a slow query, adding servers just gives you more machines running the same slow code — the per-request time stays exactly the same.

✕
"Scalability is only about handling more users."

Not quite — it also covers handling more data, more requests per user, or more geographic regions, while keeping performance and cost reasonable.

GRADED

Performance or Scalability?

Read each scenario and click the correct classification. Discuss with a neighbor before answering if you're unsure.

1. A single checkout API takes 3 seconds to respond even when only one user is on the site.
This is performance — slow even under trivial load. Adding servers won't fix a query or algorithm that's inherently slow; you need to optimize the code itself.
2. The app responds in 80ms with 100 users, but crashes or times out once traffic hits 50,000 concurrent users.
This is scalability — performance is fine at low load, the system just can't grow to handle more of it. Solve with horizontal scaling, load balancing, or caching.
3. A report job reads an entire 10GB file into memory instead of streaming it, so it's slow for every single user who runs it, regardless of how many other users are active.
This is performance — an inefficient implementation. More servers would just mean more machines doing the same slow thing.
4. A startup's database handles their first 1,000 customers fine, but as they grow to 2 million customers, writes start failing because a single database instance can't keep up.
This is scalability — the database architecture needs to grow (sharding, replicas, or a distributed database) to handle the increased data and request volume.
