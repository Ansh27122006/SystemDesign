02 · Vertical scaling

Scaling up: buy a bigger box

Why teams reach for it first
  • Zero code or architecture changes needed
  • No distributed-systems complexity — one machine, one source of truth
  • Fast to do for a small, quick win
Where it falls apart
  • Hard ceiling — eventually there's no bigger machine to buy
  • Usually requires a reboot, meaning real downtime per upgrade
  • Still a single point of failure — one box dies, everything dies
  • Cost grows faster than capacity at the high end
03 · Horizontal scaling

Scaling out: add more boxes

Add more (usually cheaper, commodity) machines behind a load balancer. Near-limitless growth and no single point of failure — but it introduces a classic trap: what happens to data that lives on just one node?

05 · Quick check

Test the room

Cold-call these live — click an option to reveal the answer on screen.

Q1. Why does vertical scaling usually cause downtime that horizontal scaling avoids?
Vertical scaling always uses slower hardware
Upgrading the one machine's resources typically requires stopping and rebooting it; adding a new node doesn't touch existing ones
Q2. A team stores user sessions in each web server's local memory, then adds a load balancer with 4 servers. What breaks?
Nothing — load balancers automatically share memory between servers
Users can get logged out or lose their session when routed to a different server that never saw their login
Q3. What's the fundamental limit of vertical scaling that horizontal scaling doesn't have?
There's a biggest machine you can buy — after that, there's nowhere left to grow
Vertical scaling can't run any database software
Vertical scaling is always more expensive from day one
Q4. What must be true about your application servers for horizontal scaling to work smoothly?
They must all run on identical physical hardware
They should be stateless, with shared data (sessions, cache) stored externally rather than on one instance
They must be written in a compiled language
