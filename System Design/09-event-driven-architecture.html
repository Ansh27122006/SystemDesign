Event-Driven Architecture

In Module 02, Order Service called Payment Service directly and waited. Event-driven architecture replaces that direct phone call with a bulletin board: Order Service posts "an order happened," and anyone interested reads it whenever they're ready — without Order Service ever knowing, or caring, who's listening.

Opening picture — a phone call vs a bulletin board

Direct phone call: Order Service calls Payment Service and stays on the line until it answers. If Payment Service is busy, slow, or down, Order Service is stuck waiting right along with it.

01 · CORE DEFINITIONS
Request/response vs Event-driven

Both are ways for services to communicate. The difference is whether the sender waits for — or even knows about — whoever handles it next.

Synchronous Request/Response

One service calls another directly and waits for a reply before continuing. The caller knows exactly who it's talking to, and is blocked until it gets an answer.

☎️ Analogy: calling someone and staying on the line until they pick up and answer.
tight temporal couplingcaller knows the calleeimmediate response
VS

Event-Driven

A service publishes an event describing something that happened. It doesn't wait for anyone, and doesn't know or care which services (if any) react to it.

📌 Analogy: pinning a notice to a shared bulletin board — you walk away immediately, and anyone interested reads it later.
temporal decouplingpublisher doesn't know subscriberseventual processing

04 · REAL-WORLD EXAMPLES
Event-driven systems in production
📡

Apache Kafka at LinkedIn

Kafka was built at LinkedIn specifically to handle massive streams of events (profile views, connections, activity) durably and in order, and is now the industry-standard backbone for event-driven systems at scale.

INDUSTRY STANDARD
🚕

Uber's trip event stream

A single "trip completed" event fans out to pricing, driver payouts, rider receipts, fraud detection, and analytics — each team owns their own subscriber, completely independent of how the trip event was originally produced.

FAN-OUT AT SCALE
🛒

E-commerce order pipelines

An "OrderPlaced" event commonly triggers inventory reservation, shipping label generation, invoice creation, and a confirmation email — four independent teams' services, none of which needed to be called directly by checkout.

COMMON PATTERN
🔔

Slack's notification fan-out

A single message-sent event needs to update the web app, mobile push notifications, unread badges, and search indexing — event-driven fan-out lets each of these evolve independently without coupling them to message-sending logic.

05 · COMMON CONFUSIONS
What students usually get wrong
✕
"Event-driven means fully decoupled — services don't depend on each other at all."

They're decoupled in time (publisher doesn't wait) but still coupled through the event's shape — if the event schema changes, every subscriber can break. That's a real, ongoing coordination cost.

✕
"Events are guaranteed to be processed in the exact order they were published."

Depends entirely on the broker and configuration. Many systems only guarantee ordering within a single partition/key, not globally — a common source of subtle bugs.

✕
"Event-driven architecture always uses a message queue like SQS or RabbitMQ."

Message queues are one implementation. Pub/sub systems like Kafka, webhooks, and even simple database triggers can all be "event-driven" in the architectural sense — the pattern is about the communication style, not one specific tool.

06 · IN-CLASS ACTIVITY
Synchronous or Event-driven?
GRADED

Which communication style fits best?

For each scenario, decide whether a direct synchronous call or an event makes more sense.

1. Checking whether a credit card has sufficient funds before confirming a purchase to the user on screen.
This needs a synchronous call. The user is waiting for an immediate yes/no answer before the checkout can proceed — this isn't something that can happen "eventually."
2. Notifying the analytics, recommendations, and email teams that an order was placed, so each can update their own systems.
This is a great fit for an event. None of these three need to respond immediately, the checkout flow shouldn't wait on any of them, and new subscribers can be added later without touching checkout code.
3. A ride-sharing app needs to know right now whether a driver is available before showing the rider a price and ETA.
This needs a synchronous call. The rider is actively waiting on screen for an immediate answer — an "eventually available" driver isn't useful here.
4. Updating a search index whenever a product's price or stock changes, across a catalog of millions of items.
This is a great fit for an event. Search index updates don't need to block the product update itself, and a queue naturally absorbs bursts of changes without overwhelming the indexing service.
