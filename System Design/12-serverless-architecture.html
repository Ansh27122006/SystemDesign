Serverless Architecture

Module 04 introduced serverless as a third option next to monolith and microservices. This module goes deep on it alone: what actually happens when a function runs, why it scales the way it does, how billing works down to the millisecond, and the one big catch — statelessness.

Opening picture — a food truck that only exists when it's needed

There's no truck parked on the street costing you money while nobody's hungry. The moment an order comes in, a truck (a function instance) appears, cooks the one order, and then vanishes — no rent, no idle staff. Order 50 things at once, and 50 trucks appear simultaneously. That's serverless in one picture.

01 · CORE DEFINITION
What actually makes something "serverless"

"Serverless" doesn't mean no servers — it means you never see them. Five traits define the model.

TraitWhat it means in practice
Event-triggeredCode runs only in response to a trigger — an HTTP request, a file upload, a schedule, a queue message.
Automatic scalingThe platform spins up as many parallel instances as needed, from zero to thousands, with no capacity planning from you.
No server managementThe provider handles the OS, patching, capacity, and infrastructure entirely — you supply only code.
Pay-per-executionBilling is based on number of invocations and execution time/memory used — not on uptime.
Stateless between callsEach invocation runs in a fresh (or possibly reused) environment — you can't reliably rely on in-memory state surviving between calls.

04 · ANIMATION
Billing down to the millisecond

Each invocation is metered individually: duration × memory allocated determines the cost, and the meter runs only while code is actually executing.

An always-on server would have cost the same flat amount whether it ran these 3 invocations or sat idle all day. Here, the bill is built purely from the sum of actual compute consumed.

05 · ANIMATION
The catch: nothing survives between calls

This trips up almost everyone the first time. A variable set during one invocation is not guaranteed to exist during the next one — even a moment later — because it might run in a brand-new instance.

Simulation — two calls, two different (possibly fresh) instances

Try it: set the counter in Call 1, then read it in Call 2. Because each invocation may land on a different, fresh instance, the counter is often gone — which is why real serverless apps store state in an external database or cache, never in local memory.

06 · TRADE-OFFS
Where serverless genuinely wins — and where it hurts

Strengths

  • Zero infrastructure management — no servers to patch, size, or keep alive
  • Scales automatically from zero to huge bursts with no configuration
  • Pay only for actual execution — no cost for idle time
  • Fast to build small, independent, event-triggered pieces of logic
VS

Weaknesses

  • Cold starts add latency after idle periods
  • Statelessness forces every bit of state into external storage
  • Most platforms cap execution time (e.g. 15 minutes) — not for long-running jobs
  • Can cost more than always-on servers under sustained, high, steady load

08 · COMMON CONFUSIONS
What students usually get wrong
✕
"I can store data in a variable and it'll be there next time my function runs."

Not reliably. Instances can be reused (giving the illusion this works in testing) or replaced entirely — production code should never depend on in-memory state surviving between invocations.

✕
"Serverless functions can run as long as I need them to."

Every major platform caps execution time — AWS Lambda's limit is 15 minutes, for example. Long-running jobs need a different architecture entirely (a container, a queue-based worker, etc).

✕
"Serverless" only means "functions" (FaaS).

The broader "serverless" ecosystem also includes serverless databases, storage, and queues that scale and bill the same way — the FaaS function is just the most visible piece.

09 · IN-CLASS ACTIVITY
Good fit or bad fit for serverless?
GRADED

Should this workload run as a serverless function?

For each scenario, decide whether serverless is a reasonable choice.

1. A function that validates and resizes a profile photo the instant a user uploads one, a few thousand times a day at unpredictable moments.
This is a good fit. Short-lived, event-triggered, unpredictable timing — exactly the profile serverless functions are built for.
2. A video encoding job that regularly needs to run for 45 minutes to process a single long file.
This is a bad fit for standard serverless functions — most platforms cap execution around 15 minutes. This calls for containers or a dedicated worker instead.
3. A backend that needs to keep an in-memory cache of recent lookups, hit thousands of times per second, where every millisecond of latency matters.
This is a bad fit. Serverless's statelessness works against an in-memory cache design, and sustained high-frequency traffic often costs more on a per-invocation model than an always-on service.
4. A nightly job that pulls a report, emails it to a distribution list, and finishes in under a minute.
This is a good fit. A short, scheduled, infrequent task is close to a textbook serverless use case — paying for an always-on server just to wait for once-a-day work would be wasteful.
