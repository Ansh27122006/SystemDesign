Performance vs Scalability

Performance is how fast one server answers right now. Scalability is whether the system keeps that speed as load grows, by adding resources. A fast system isn't automatically a scalable one.

Performance

How quickly a single unit of work is completed under a given load — measured in response time, CPU cycles, or requests handled per instance.

fixed load, one node
VS

Scalability

The system's ability to maintain acceptable performance as load increases, usually by adding more resources (scale out/up).

growing load, N nodes

Classify the problem

For each scenario, decide: is this a performance problem or a scalability problem? Click your answer.

1. A single checkout API takes 3 seconds to respond even when only one user is on the site.
This is performance — it's slow even under trivial load. No amount of adding servers fixes a query that's inherently slow; you'd need to optimize the code, query, or algorithm itself.
2. The app responds in 80ms with 100 users, but crashes or times out once traffic hits 50,000 concurrent users.
This is scalability — performance is fine at low load, the system just can't grow to handle more of it. This calls for horizontal scaling, load balancing, or caching.
3. A report-generation job reads an entire 10GB file into memory instead of streaming it, so it's slow for every single user who runs it.
This is performance — an inefficient algorithm/implementation. Adding more servers would just give you more machines doing the same slow thing.

Latency vs Throughput

Latency is the travel time for one request. Throughput is how many requests get through per second. Think of a highway: latency is how long one car takes to reach the other end; throughput is how many cars pass per minute. You can raise one without touching the other.

Latency

Time for a single request to travel from source to destination and back. Measured in milliseconds (ms). Lower is better.

per-request delay
VS

Throughput

Volume of requests a system can process in a given time window. Measured in requests/sec. Higher is better.

system-wide volume

Match the analogy

Which metric does each real-world example map to — latency or throughput?

1. A supermarket has one checkout counter. Each customer is served quickly (30 seconds), but only one line exists.
Low latency, low throughput. Each individual customer is served fast, but because there's only one counter, the total number of customers served per hour is capped.
2. A cargo ship takes 3 weeks to cross the ocean, but it carries 20,000 containers per trip.
High latency, high throughput. Each individual container takes 3 weeks (slow), but the sheer volume moved per trip is enormous — this is exactly how batch data pipelines trade latency for throughput.
3. A video call has audio that arrives 400ms late, making conversation feel laggy, even though the call never drops.
This is a latency problem — real-time interaction cares about per-packet delay, not total volume. This is why video calls use UDP and prioritize speed over completeness.

Availability vs Consistency

The CAP theorem: when a network partition happens, you must choose. Availability keeps answering requests, even if the answer might be stale. Consistency guarantees every read reflects the latest write — even if that means refusing to answer.

Availability (AP)

Every request gets a response, even during a network partition — though it might not reflect the most recent write.

always answers
VS

Consistency (CP)

Every read reflects the latest write. During a partition, the system may refuse requests rather than return stale data.

always correct

CP or AP?

For each real system, decide whether it should favor consistency or availability when a partition hits.

1. A bank's system processing money transfers between accounts.
Favor consistency. Showing the wrong balance, or allowing a double-spend during a partition, is far worse than the system briefly refusing a transaction.
2. A social media "like" counter shown under a post.
Favor availability. If the like count is off by a few for a moment, nobody's harmed — but the feed going down entirely would upset every user.
3. DNS — translating a domain name to an IP address.
Favor availability. DNS is designed to always answer, even with slightly stale records (that's what TTLs are for) — an unreachable DNS server breaks the entire internet for its users.
