Latency vs Throughput

Latency asks "how long does one request take?" Throughput asks "how many requests get through per second?" You can improve either one without touching the other — this module makes that split impossible to un-see.

Opening analogy — the highway

1 lane, short road: one car at a time, but it arrives fast. Low latency, low throughput.

01 · CORE DEFINITIONS
Two different questions about speed

People say "the system is slow" to mean two totally different things. Splitting them apart is the single most useful habit in this whole course.

Latency

The time it takes for one single request to travel from client to server and back — the delay experienced by one user, for one action.

🚗 Analogy: how long it takes one car to drive from one end of the highway to the other.
milliseconds (ms)round-trip timep50 / p95 / p99"time to first byte"
VS

Throughput

The volume of requests a system can process in a given window of time — how much work gets done overall, regardless of any single request's delay.

🚗 Analogy: how many cars pass a checkpoint on the highway every minute.

03 · ANIMATION
How throughput actually gets built from latency

Here's the core relationship students need to internalize: throughput isn't the opposite of latency — it's what you get when you run many requests in parallel. This is a simplified version of Little's Law.

Throughput ≈ Concurrency ÷ Latency
More parallel workers or lower per-request latency both raise throughput. This is why adding servers (module 01) and reducing latency both help throughput — they attack the same formula from different sides.

06 · REAL-WORLD EXAMPLES
Where teams design around one or the other
🎮

Competitive online gaming

A first-person shooter cares almost entirely about latency — 30ms vs 150ms of lag is the difference between winning and losing a duel. Total players served per second matters far less than each player's round-trip time.

LATENCY-CRITICAL
🎬

YouTube video transcoding

When you upload a video, it might take minutes to process (high latency for that one job) — but YouTube's pipeline transcodes hundreds of thousands of videos simultaneously across its fleet. Throughput at scale matters far more than any single video's processing time.

THROUGHPUT-CRITICAL
📈

High-frequency stock trading

Firms spend millions shaving microseconds off latency — even laying private fiber in straight lines between exchanges — because being 1ms faster than a competitor to react to a price change is worth more than handling more trades per second.

LATENCY-CRITICAL
🌐

Content Delivery Networks (CDNs)

A CDN like Cloudflare or Akamai is a rare case of optimizing both at once: caching content at edge locations near users cuts latency, while spreading traffic across thousands of edge servers worldwide massively increases total throughput.

BOTH, BY DESIGN
07 · COMMON CONFUSIONS
What students usually get wrong
✕
"Higher throughput automatically means lower latency."

False — and often the opposite. Batch systems maximize throughput by grouping requests together, which can add latency for any individual item in the batch (it waits for the batch to fill up).

✕
"They're just two names for 'speed'."

Not the same axis. A system can feel instant to one user (low latency) while completely failing to keep up with thousands of users at once (low throughput), or vice versa.

✕
"Adding more servers always helps both."

More servers raise throughput (more parallel capacity) but do nothing for the latency of a single request — the round-trip to one server, one database query, one disk read stays exactly the same.

08 · IN-CLASS ACTIVITY
Which metric matters most here?
GRADED

Latency-critical or Throughput-critical?

For each system, decide which metric the engineering team should optimize for first.

1. A video call app where audio arrives 400ms late, making conversation feel awkward — even though the call never drops a single packet.
This is a latency problem. Real-time interaction cares about per-packet delay, not total volume — which is why video calls use UDP and favor speed over completeness.
2. A nightly analytics job that processes 50 million log lines. Each run takes 4 hours, and that's totally fine as long as it finishes before 6am.
This is throughput-critical. Nobody's waiting on any single log line — the goal is maximizing total volume processed within the batch window, so parallel processing across many machines matters most.
3. An autocomplete search box that must show suggestions as the user types, or it feels broken.
This is latency-critical. Even a 300ms delay per keystroke is noticeable and frustrating — this is why autocomplete backends are built on ultra-fast in-memory indexes.
4. A payment processor on Black Friday needs to handle 40,000 transactions per second across all customers combined, even if each individual transaction takes a couple hundred extra milliseconds during peak.
This is throughput-critical. The business risk here is dropped or failed transactions at scale, not a few hundred extra milliseconds on any one purchase.
