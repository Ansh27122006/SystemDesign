Monolithic Architecture

The oldest and still most common way to build software: everything — the UI, the business logic, the data access — lives in one codebase, deployed as one unit. Before learning why teams move away from it, it's worth understanding why it's usually the right place to start.

Opening picture — one building, all departments inside

Every "floor" — the web UI, the order logic, the payment logic, the inventory logic — lives inside the same building (the same running process). They call each other directly with normal function calls, share the same elevator (the same database), and the whole building opens or closes for renovation together. There's no separate "payments building" you could shut down without affecting the rest.

01 · CORE DEFINITION
What actually makes something "a monolith"

Four traits define a monolithic architecture, and they all follow from one core idea: it's a single deployable unit.

TraitWhat it means in practice
Single codebaseAll features live in one repository, usually one programming language/framework.
Single deploymentShipping any change — big or tiny — means building and deploying the entire application at once.
Shared databaseAll modules typically read and write the same database directly, often the same tables.
In-process callsModules call each other as normal function calls in memory — no network hop, no serialization.

05 · TRADE-OFFS
Where a monolith genuinely wins — and where it hurts

Strengths

  • Fast to build and ship in the early days — no network boundaries to design around
  • Simple to test end-to-end and to debug (one process, one set of logs)
  • No distributed-systems failure modes (partial failure, network partition, retries)
  • Easier for a small team to reason about the whole system at once
VS

Weaknesses

  • Any change requires a full rebuild and redeploy of everything
  • Can't scale one hot feature independently of the rest
  • Large teams collide constantly working in the same codebase
  • A bug or memory leak in one module can take down the entire application
06 · REAL-WORLD EXAMPLES
Monoliths in serious production use
🛍️

Shopify's "modular monolith"

Shopify famously runs a massive Ruby on Rails monolith serving over a million merchants, deliberately organized into strict internal modules — proving a monolith can scale to enormous size if the internal boundaries are kept clean.

STILL MONOLITHIC
📈

Stack Overflow's famously small footprint

For years, Stack Overflow served enormous global traffic from just a handful of servers running a well-optimized monolith — a reminder that "monolith" doesn't mean "can't scale," it means "scales as one unit."

EFFICIENT AT SCALE
🚀

Almost every successful startup, early on

Basecamp, early Airbnb, early Facebook — nearly every company that later became known for scale started as a single monolithic application, because it let a tiny team ship fast before the complexity of distribution was worth paying for.

🐦

Twitter's early "Fail Whale" era

Twitter's original Ruby on Rails monolith famously struggled under viral growth — a real example of a monolith reaching the point where its single-unit scaling model became the actual bottleneck, motivating their move toward services.

07 · COMMON CONFUSIONS
What students usually get wrong
✕
"Monolith" automatically means "bad, legacy, unmaintainable."

A monolith can be extremely well-organized internally (see: modular monolith). "Monolithic" describes the deployment model, not the code quality.

✕
"Monoliths can't scale."

They scale differently — by running more full copies behind a load balancer (module 01: horizontal scaling) — not that they can't scale at all. Stack Overflow served billions of monthly page views from a monolith for years.

✕
"You should avoid monoliths and start with microservices."

Most experienced engineers recommend the opposite: start with a well-structured monolith, and split out services only once you have a concrete, specific reason to — the added complexity of a distributed system isn't free.

08 · IN-CLASS ACTIVITY
Good fit or bad fit for a monolith?
GRADED

Should this team choose a monolith?

For each scenario, decide whether a monolithic architecture is a good starting choice.

1. A 4-person startup building an MVP to validate an idea, aiming to ship in 6 weeks.
This is a good fit. Small team, tight timeline, unproven product — the speed and simplicity of a monolith heavily outweighs any scaling concerns they don't have yet.
2. A company with 40 engineering teams, each needing to deploy their own feature multiple times a day without waiting on or breaking anyone else's code.
This is a bad fit for a pure monolith. At this scale of team count and deploy frequency, shared deploys become a constant bottleneck — this is the scenario where splitting into independently deployable services earns its complexity.
3. An internal admin tool used by 20 employees at a mid-size company, with simple, predictable traffic.
This is a good fit. Low traffic, small user base, no reason to pay the operational cost of a distributed system for a tool like this.
4. A platform where the "video transcoding" feature needs to scale to thousands of CPU-heavy servers, while the "user profile" feature needs almost none.
This is a bad fit for a pure monolith — wildly different scaling needs between features is a classic, concrete reason to split the CPU-hungry piece into its own independently scalable service.
