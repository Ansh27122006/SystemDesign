How a Web Page Loads

Typing a URL and hitting enter feels instant. Underneath, it's a relay race: a lookup, two handshakes, a request, server work, a response, and then a whole separate pipeline just to turn HTML/CSS into pixels. This module walks the whole trip twice — once as a detailed 2D diagram, once as a spatial 3D scene.

01 · THE BIG PICTURE
Two separate phases, back to back

Everything that happens when a page loads falls into one of two phases. Both matter, and slowness in either one is felt by the user as "the site is slow."

Network Phase

Getting bytes from a server somewhere on the internet onto the user's machine: finding the server's address, establishing a secure connection, sending a request, and waiting for a response.

Rendering Phase

Turning the raw HTML/CSS/JS bytes that just arrived into actual pixels on screen, and making the page respond to clicks and scrolls.

04 · REAL-WORLD EXAMPLES
Where engineers actually speed this up
🌐

CDNs shortcut the network phase

Content Delivery Networks cache your site's files on servers physically close to each visitor, cutting DNS + connection + response time — often the single biggest real-world speed win for a global audience.

NETWORK PHASE
⏱️

async / defer on script tags

A plain <script> tag blocks HTML parsing until it downloads and runs. Adding defer or async lets the browser keep building the DOM in parallel, which is why almost every modern site uses one of them.

RENDERING PHASE
📦

Minified & compressed CSS/JS

Smaller files mean less to download in the network phase and less for the browser to parse in the rendering phase — this is why production builds strip whitespace, shorten variable names, and gzip everything.

BOTH PHASES
🖼️

Lazy-loading images

Images below the fold are told to load only once the user scrolls near them (loading="lazy"), so the initial render finishes faster instead of waiting on content nobody's looking at yet.

05 · COMMON CONFUSIONS
What students usually get wrong
✕
"The whole HTML file has to arrive before anything shows up."

Not quite — browsers parse HTML incrementally as bytes stream in, which is why pages can render progressively, top to bottom, rather than all at once at the very end.

✕
"Page load is done once the HTML response arrives."

That's roughly the halfway point. Building the DOM, fetching CSS/JS, computing layout, painting, and compositing all still have to happen before the user sees or can interact with anything.

✕
"JavaScript always blocks rendering."

Only true for a plain, synchronous <script> tag in the document head. async and defer both let parsing continue while the script downloads.

06 · IN-CLASS ACTIVITY
Test the sequence
GRADED

What happens next?

For each question, pick the correct answer about the loading sequence.

1. The browser has the domain name but no IP address yet. What has to happen before any connection can be made?
Correct answer: DNS lookup. The browser must translate the human-readable domain into an IP address before it can even attempt to connect to anything.
2. The HTTP response with the HTML has just arrived at the browser. What's the very next thing that happens?
Correct answer: parsing HTML into the DOM. The rendering phase always starts with turning the raw HTML text into a structured tree the browser can work with.
3. The browser already has the DOM and CSSOM combined into a render tree. What must happen before anything can be painted?
Correct answer: layout. The browser needs to know exactly where and how big every element is before it can fill in any pixels.
4. A page has a large JavaScript file that isn't needed until after the page is visible. What lets the HTML keep parsing while that script downloads?
Correct answer: defer/async. Without one of these, a plain script tag halts HTML parsing until the script finishes downloading and executing.
